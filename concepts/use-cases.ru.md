# Случаи использования

## A. Несколько агентов в одном проекте

Основной случай. Над одним репозиторием работают несколько агентов:

- **разные инструменты** — Claude Code и Codex в одном репозитории;
- **параллельные сессии по зонам** — отдельные агенты на backend, frontend, тесты;
- **разные машины и люди** — агенты разных разработчиков;
- **исполнитель и ревьюер** — обычно это одна сессия одного агента, хаб там не нужен; если их разделить — ревьюер пишет вопросы и предложения через обсуждения.

Документация им доступна: своя в wiki, внешняя в docs. Нужна координация:

| Потребность | Как решает хаб |
|---|---|
| «Я поменял формат ответа API — проверь клиент» | Обсуждение вида `note`, адресованное агенту frontend |
| «Почему здесь сделано так?» — через неделю, в другом инструменте | Итоги обсуждений по документу (`refs`) |
| «Что поменялось в `wiki/api/` с моей прошлой сессии?» | Функция `changes` |
| Два агента берутся за один раздел | Функция `claims`: отметка «работаю над `wiki/api/auth.md`» |
| Предложение изменить чужую зону | Обсуждение `proposal`, решает владелец зоны |

Пример — [examples/single-project-agents](../examples/single-project-agents.ru.md).

## B. Межпроектный контракт

**Пример:** документация «Внешний контур портала для мобильного приложения» (`mobile-app`). Она описывает API портала для мобильной команды и хранится **в wiki проекта портала** (`wiki/mobile-app/`): правится из одного места и приходит с клоном хаба.

| Агент | Где работает | Права в проекте `portal` |
|---|---|---|
| агент backend | репозиторий портала | участник; **владелец зоны** `wiki/mobile-app/`; правит документацию через `doc-hub wiki write` |
| агент мобильного приложения | свой репозиторий, без доступа к коду портала | участник с доступом **только к пути** `wiki/mobile-app/` |

Работа:

1. Мобильный агент читает контракт: `doc-hub wiki read`. Доступ к коду портала ему не нужен.
2. Хочет другой формат — открывает `proposal` со ссылкой на документ.
3. Владелец зоны принимает или отклоняет, правит документ в wiki, отмечает предложение `applied` с коммитом хаба.
4. Мобильный агент через `changes` видит изменения контракта.

Получатель документацию не правит: изменение контракта проходит через согласование. Отдельного «проекта-контракта» нет — это зона в проекте источника.

Пример — [examples/contract-zone](../examples/contract-zone.ru.md).

## C. Чтение чужой документации

Проект регистрируется в хабе, чтобы его документацию могли читать агенты других проектов и люди — вместе с документацией остальных проектов (в Obsidian, Web, CLI) — как docs, см. [docs-sources](../specifications/docs-sources.ru.md). Функции не нужны. Агенту выдаётся роль `reader`, при необходимости — с ограничением путями.

Это частный случай: сам по себе он даёт немного (чтение можно организовать и клоном репозитория), но не требует от проекта ничего, кроме регистрации.
