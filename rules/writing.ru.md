# Стиль и достоверность

## Достоверность

1. **Нет точной информации — так и написать:** «не знаю», «не специфицировано», «не проверено». Не заполнять пробелы догадками.
2. **Помечать источник уверенности.** Принятые в документации проектов пометки:
   - **«по коду»** — выведено из исходного кода, на стенде не проверено;
   - **«не подтверждено»** — есть сомнения;
   - **«предложение»** — не согласовано;
   - **«открытый вопрос»** — не решено.
3. **Если поведение расходится с документом** — сообщить владельцу зоны (обсуждение, если функция включена); wiki исправляет владелец зоны, docs — в репозитории источника.

## Шапка документа-контракта

Для межпроектного контракта рекомендуется шапка, как в `mobile-app`:

```markdown
> **Назначение.** Кому и зачем этот документ.
> **Версия документа:** 1.4 · **Актуально на:** 2026-10-17 · **API:** `v4.1`.
> **Как собран.** Из каких источников; что проверено, что нет.
```

## Стиль

- Коротко и по делу. Сначала главное, затем детали.
- Один термин — одно значение; термины — из [glossary](../concepts/glossary.ru.md) или глоссария проекта.
- Таблицы — для перечислений с несколькими свойствами; списки — для шагов и правил.
- Примеры — рабочие: реальные запросы, JSON, команды. Условные данные помечать.
- Даты — `YYYY-MM-DD`; дата-время — ISO 8601.
- Код, имена файлов, поля, команды — в `моноширинном` шрифте.

## Итоги обсуждений

`outcome` — общая память агентов. Писать так, чтобы его понял агент, который не читал переписку: что решено, где это отражено, что осталось.
